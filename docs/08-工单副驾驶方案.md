# 工单副驾驶 · 方案

| 项 | 内容 |
|---|---|
| 版本 | v1.0（2026-11-25 已确认，同日做完，实测见 docs/05 §34） |
| 范围 | 客服在后台回复买家时，点一下让 AI 按这段对话、资料和订单情况起草一份回复，客服改完再发。先在模拟店铺上做 |
| 不做 | AI 直接替客服发出去；在接入方的工单系统里起草（模拟店铺没有工单后台，真实接入方以后再说）；自动判退款、补发 |
| 前提 | 人工接管已经做完（docs/07），回复框在后台会话页 |

## 1. 为什么要

转人工的事都是要人判断的：退款、补发、封号、付错。客服每次要翻对话、查规则、看订单，再组织语言。副驾驶把这些先拼好，客服只做判断和修改。

## 2. 客服怎么用

- 后台会话页的回复框旁边加一个「AI 起草」按钮。
- 点了以后几秒内，草稿填进回复框（不会自动发出），客服可以改。框下面列出起草时用到的资料标题和订单号，方便客服核对。
- 草稿里拿不准、要客服决定的地方写成 **【待确认：……】**，比如「【待确认：是否在保】」。有这种标记时「发送」按钮旁提示一句「还有待确认的地方」，但不拦着。
- 回复框旁另有「复制」：有工单的事客服可能要到店铺的工单里回，复制过去就行。

## 3. 草稿是怎么来的

起草时一次调模型，喂给它：

| 喂什么 | 从哪来 |
|---|---|
| 最近的对话（买家、AI、客服的话，最多 20 条） | 消息表 |
| 转人工的摘要、工单号或邮箱 | 转人工表 |
| 对话里查过的订单情况 | 工具调用记录里 `my_orders` 最近一次的结果。**访客令牌不存库，后台不能重新查订单**，所以是买家当时看到的状态；草稿下面写明「订单信息是 ×× 时的」，提醒客服到店铺核对 |
| 相关资料 | 用买家最近的问题和转人工摘要各检索一次（和对话用同一个索引、同一个配方），取前 5 块 |

提示词的要点：

- 用客服的口吻，称「我们」，可以说「我来处理」「我核实一下」，这是和 AI 回答不同的地方。
- 规则照资料说；**要店铺拍板的（退不退、补不补、算不算在保）不替客服下结论**，写成【待确认】，并把相关规则列在旁边给客服参考。
- 买家用什么语言就用什么语言。
- 不复述卡密、密码；订单只提订单号和状态。

## 4. 接口和表

| 改动 | 说明 |
|---|---|
| `POST /api/chats/{id}/draft` | 后台：起草，返回 `{text, sources: [{title, document}], orders_at, open_points}`。不存库 |
| `chat/copilot.py` | 新模块：拼材料、调模型、找出【待确认】。和 `chat/agent.py` 分开，不复用对话循环（副驾驶不调工具、不流式） |
| 用量 | 记进当天的用量和花费；到了每日上限也照样能起草（这是客服自己用的，见§6 第 4 条） |
| 表 | 不改 |

## 5. 怎么验收

- 单元测试：材料拼对了（含订单记录时间、资料编号）、【待确认】能找出来、草稿不存库。
- 用评测题里 9 道「该转人工」的题：先走一遍对话转成人工，再起草，用另一次模型调用检查三条：没有替店铺下结论、规则没说错、该待确认的地方标了。结果记进 docs/05，每份草稿也存下来供人工抽查。
- 浏览器里起草、修改、发送走一遍。

粗估：1.5–2 天。

## 6. 定下的做法

1. 草稿直接填进回复框，客服改完发。
2. 订单信息用对话当时查到的记录，注明时间；不让接入方另做接口。
3. 有【待确认】只提示，不拦着发。
4. 起草算进每日用量，到了上限也照样能用。
5. 先不记采用情况。
