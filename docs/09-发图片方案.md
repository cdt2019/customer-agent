# 发图片 · 方案

| 项 | 内容 |
|---|---|
| 版本 | v1.0（2026-11-25 已确认，同日做完，实测见 docs/05 §35） |
| 范围 | 买家在聊天窗里发截图（比如卡密报错、付款记录、封号提示），客服在后台看得到。先在模拟店铺上做 |
| 不做 | 客服给买家发图；发视频和其他文件；AI 看懂图片（见§7 第 1 条） |
| 前提 | 人工接管（docs/07）已经做完：图片主要是给接手的客服看的 |

## 1. 一个限制先说清楚

现在用的 `deepseek-flash` 只认文字，**看不懂图片**。所以第一版里 AI 只知道「买家发了一张图」，不知道图上是什么；图是给人工客服看的。要让 AI 读图，得换支持图片的模型（或者先用文字识别把图上的字提出来），这是选型变化，另行讨论（§7 第 1 条）。

## 2. 买家这边

- 聊天窗输入框左边加一个「图片」按钮，选一张图发出；也可以直接粘贴截图。
- 发出后对话里显示缩略图，点开看大图。
- 一次发一张；图片和文字分开发（一条消息要么是一张图，要么是文字）。
- AI 收到图片时这样回（§7 第 3 条）：说明自己看不到图片内容，请买家用一两句话说一下图上的问题；如果是卡密报错、付款、封号这类要人看的事，建议转人工。**不自动转**，按现在的规矩由模型判断。
- 客服在接（`staff`）时，图片直接给客服，不经过 AI。

## 3. 客服这边

- 后台会话页里图片显示成缩略图，点开看原图。
- 转人工的摘要里写明「买家发了 N 张图片」，提醒客服去会话里看。
- 工单副驾驶起草时也只知道「买家发了一张图片」。

## 4. 安全和存储

| 项 | 做法 |
|---|---|
| 格式 | 只收 JPG、PNG、WebP（§7 第 2 条）。按文件内容判断格式，不信后缀 |
| 大小 | 单张最大 5MB；长边超过 2048 像素的缩小 |
| 去掉隐私信息 | 一律重新编码（Pillow 打开再存），拍摄位置、设备这些元数据都去掉；动图只留第一帧 |
| 数量 | 每个对话最多 5 张；AI 在回答时，发一张图算一次提问（AI 要回一句），客服在接时不算 |
| 存哪 | 磁盘上 `IMAGES_DIR`（环境变量，线上放 `/data` 卷里），随机文件名；库里只记文件名、尺寸和属于哪条消息 |
| 谁能看 | 后台登录后能看；买家只能经接入方看自己会话里的图。返回图片时带 `nosniff` 和 `sandbox`，和看导入原文件一样 |
| 保留 | 和聊天记录一样 90 天，到期清理时连文件一起删（§7 第 4 条） |
| 解析放哪 | Pillow 解码放在单独的子进程里，带超时，和解析导入文件一个道理（图片也是不可信的输入） |

## 5. 接口和表

| 改动 | 说明 |
|---|---|
| 新表 `images` | 编号、所属会话和消息、文件名、宽高、字节数、时间；随会话一起删 |
| 消息 | 发图片时存一条 `user` 消息，文字是「[图片]」，挂一张图 |
| `POST /v1/conversations/{id}/images` | 接入方转发：上传一张图（multipart），带访客令牌；回 SSE，和发文字一样（客服在接时只回 `user` 和 `done`） |
| `GET /v1/conversations/{id}/images/{image_id}` | 接入方转发：买家看自己会话里的图 |
| `GET /api/chats/images/{image_id}` | 后台看图 |
| 历史接口 | 消息里多一个 `image`（编号、宽、高），聊天窗和后台据此显示 |
| 技术方案 §5.4 | 加两个转发接口；接入方要做的是原样转发这两个请求，并检查会话归这个浏览器 |
| 模拟店铺 `relay.py` | 加这两个转发 |

## 6. 怎么验收

- 单元测试：只收图片格式；超大的拒；元数据被去掉（造一张带 GPS 的 JPG 检查）；超过 5 张拒；到期清理删文件；别人的会话看不到图。
- 端到端加一段：买家发图 → AI 回复说看不到图、建议描述或转人工 → 后台看得到这张图。
- 浏览器里两边走一遍，包括粘贴截图。

粗估：2–3 天（服务端 1、聊天窗 0.5、后台 0.5、模拟店铺和测试 0.5–1）。

## 7. 定下的做法

1. 第一版只给人看，AI 只知道买家发了图。
2. JPG、PNG、WebP，单张 5MB，每个对话最多 5 张。
3. AI 收到图片：说明看不到，请买家用文字描述；要人看的事建议转人工，不自动转。
4. 和聊天记录一样保留 90 天。
5. 客服给买家发图先不做。
