# 部署

一台装了 Docker（带 compose）的 Linux 服务器就能跑整套。下面的命令都在仓库的 `deploy/` 目录里执行。

## 1. 有什么

| 容器 | 做什么 | 端口 |
|---|---|---|
| `api` | 客服服务：对话接口 `/v1`（给接入方）和后台接口 `/api` | 只在内部网络 |
| `admin` | Caddy：管理后台的页面，`/api` 转给 `api` | 发布在本机 `127.0.0.1:18080` |
| `postgres` | 会话、知识库、评测这些数据 | 只在内部网络 |
| `qdrant` | 向量库，设了访问密钥 | 只在内部网络 |
| `demo` | 模拟店铺，代替接入方；接真实接入方后不用起 | 发布在本机 `127.0.0.1:18100` |

数据在三个卷里：`pgdata`（数据库）、`qdrant`（向量）、`data`（向量模型、Docling 的模型、上传的原文件）。

内存：向量模型 bge-m3 在处理器上用全精度，`api` 约 2.5GB；整套约 3GB。`compose.yaml` 给每个容器设了上限，并把它们放进 systemd 资源组 `customer-agent.slice`（`CGROUP_PARENT` 可改）。

## 2. 第一次部署

**准备**

1. 把仓库放到服务器上（比如 `/opt/customer-agent`）。`admin/dist` 和 `widget/dist` 是打包好的页面，要在开发机上先 `pnpm build`（后台用 `pnpm exec vite build`）再一起拷过去。
2. 建资源组（只做一次）：

   ```
   cat > /etc/systemd/system/customer-agent.slice <<EOF
   [Slice]
   MemoryMax=3584M
   EOF
   systemctl daemon-reload && systemctl start customer-agent.slice
   ```

   systemd 把名字里的短横线当层级，它实际在 `customer.slice/customer-agent.slice` 下，上限照样生效。不想单独限内存就在 `.env` 里把 `CGROUP_PARENT` 设成已有的资源组。

3. `cp .env.example .env`，填上密钥（`openssl rand -hex 24`），`chmod 600 .env`。店铺不在东八区的，设 `TIMEZONE`（每天的限额和统计从那里的零点开始）；服务器和数据库自己是什么时区都不影响。

**起服务、建索引**

```
docker compose build
docker compose up -d postgres qdrant api demo                  # api 启动时自动升级数据表
docker compose exec api agent fetch-model BAAI/bge-m3          # 约 2.3GB，按官方 sha256 核对
docker compose exec api agent sync shop-help shop              # 从接入方的帮助文章接口同步（§5.2）
docker compose exec api agent index shop-help v1               # 输出里有索引编号
```

以后帮助文章改了，在后台数据集页点「同步」就行（来源记住了是 shop）。

下模型、建索引要几分钟。SSH 断了之后 `docker compose exec` 起的进程还会在容器里接着跑，所以长命令放后台跑（`setsid nohup … &`），断了别马上再起一份：两份同时下同一个模型会把文件写坏（校验会发现并删掉，但要重下）。

把索引编号写进 `.env` 的 `INDEX_ID`，再起后台，并让模拟店铺读到新的编号：

```
docker compose up -d admin
docker compose up -d --force-recreate demo
```

**看一眼**

后台和店铺只发布在服务器本机。在自己电脑上开一个 SSH 隧道：

```
ssh -N -L 18080:127.0.0.1:18080 -L 18100:127.0.0.1:18100 <服务器>
```

然后打开 http://localhost:18080 （后台，密码是 `.env` 里的 `ADMIN_PASSWORD`）和 http://localhost:18100 （店铺）。聊天窗的常见问题一开始是空的，在后台「接入方」页填上。用 localhost 打开时登录 cookie 照常能用；要用别的域名对外开放，前面放一个带 HTTPS 的反向代理。

## 3. 更新

```
# 拷新代码过去后
docker compose build && docker compose up -d
```

数据表变了 `api` 启动时会自己升级。只换了后台页面（`admin/dist`）不用重启。

## 4. 备份

```
docker compose exec postgres pg_dump -U customer_agent customer_agent | gzip > backup-$(date +%F).sql.gz
```

向量库可以随时从数据库里的文档重建（`agent index`），不用备份；模型可以重新下。

## 5. 接真实接入方

- `SHOP_URL` 改成接入方的店铺接口（技术方案 §5.2），`SHOP_API_KEY` 和对方约定。
- 接入方的后端在内部网络里调 `api:8000/v1`，带 `SERVICE_API_KEY`。`api` 不对外发布端口。
- 不再起 `demo`。

## 6. Telegram 渠道（可选）

见 [docs/10](10-Telegram方案.md)。

1. 用店铺的 Telegram 账号找 @BotFather，发 `/newbot`，起名字，拿到令牌。
2. 在 `.env` 里填 `TELEGRAM_BOT_TOKEN`（令牌）和 `TELEGRAM_INDEX_ID`（用哪个索引回答，和模拟店铺的 `INDEX_ID` 一样填编号），然后 `docker compose up -d api`。
3. 服务启动后自己去 Telegram 拉消息，不用公网地址，也不用对外开端口。后台「接入方」页的运行信息里显示「@机器人名字」就是连上了。
4. 服务器连不上 Telegram 时设 `TELEGRAM_PROXY`；能直连就不用设（测试服务器上直连可用，见 docs/05 §36）。
